# 扩展点与插件契约（设计稿 v0.1 · 2026-09-16）

> **要解决的问题**：平台**覆盖不了所有工艺设备**。每来一台新机、一个新工艺域、一种新仪器导出格式，
> 都不该等发版、更不该让工程师去改仓库代码 —— 但也不能因此变成"每台设备一套私有口径"。
>
> **一句话原则**：**能力可以外接，口径闸必须留在中心。**
> 插件只能**产出提案/包/记录**，落库一律过同一道闸（`build_core` 拒收码 · 机台口径闸 · `validate_tool_ids`）。

---

## 一、两层扩展（先分层，再谈框架）

| | **T1 · 数据扩展** | **T2 · 代码扩展** |
|---|---|---|
| 装什么 | 机台清单/型号/别名 · 设备模板 · 参数与公式 · 影响规则 · 工艺目录 · 上传表格的列映射 | 机台菜单/配方解析器 · 仪器原始格式适配器 · 优化/建模算法 · 版图(GDS)生成 · 新设备的导出映射 |
| 谁来装 | 工程师自己（界面 / 库文件） | **管理员**装（审批 + 留痕） |
| 怎么生效 | 立刻（读库即生效，带版本留痕） | 按路径加载 + 校验 manifest |
| 失效风险 | 口径写错（可见、可回滚） | 能执行代码（必须隔离 + 只读边界） |
| 该不该多做 | **优先做这一层** | 只做"必须执行代码"的那几个点 |

**判据（决定一个扩展点归哪层）**：这东西能不能用**一张表 + 一段映射**表达？
能 ⇒ T1；不能（要跑算法/要解析私有二进制格式）⇒ T2。

## 三、插件契约（v0.1 · 最小集）

一个 T2 插件＝**一个目录 + 一份 manifest + 一个入口**：

| manifest 字段 | 说明 | 缺失/不符的后果 |
|---|---|---|
| `name` | 唯一名（装载时冲突即拒） | 拒装 |
| `api_version` | 插件写它针对的宿主接口版本（如 `1`） | **版本不符即拒装**（宁可装不上，也不要在运行期炸） |
| `kind` | 扩展点类型（`menu_parser` / `ingest_adapter` / `exporter` …） | 未知 kind 拒装 |
| `entry` | 入口（模块:函数）；装载时**导入即校验**签名 | 导入失败 ⇒ 该插件标记为红，不影响其它 |
| `capabilities` | 它产出什么（如 `propose_rows` / `normalize_columns`） | 缺则判为无效 |
| `requires` | 依赖（宿主版本 / 其它能力 / 外部二进制） | 缺依赖 ⇒ 拒装并出声 |
| `writable` | **固定为 false**：插件不得直接写数据资产 | 出现 true 直接拒装（红线做成字段） |

**四条纪律**（与 DSH 那套里真正有用的部分对齐）：

1. **只读边界**：插件只能返回**提案 / 记录 / 文件包**；写入一律由宿主经中心闸完成
   （`build_core` 拒收码 · 机台口径闸 · `validate_tool_ids`）。
2. **失败隔离**：一个插件抛错只影响它自己那条路径；服务继续跑，`/api/health` 报出"某插件红"。
3. **副作用可回收**：装载即注册清理钩子（清缓存 / 删临时文件 / 关句柄），卸载即执行。
4. **审批 + 留痕**：装/卸/升级插件是**管理员动作**，进现有 audit（谁装的、谁用的、什么时候）。

## 四、落地三步（每步独立可验收）

| 步 | 做什么 | 验收判据 | 估时 |
|---|---|---|---|
| **1** | **清单外置**：机台清单/型号/别名从代码挪到数据（工单已在架上） | 新增一台机**不改仓库代码**即可被识别；机台口径闸仍然拦得住未登记名 | 0.5–1 天 |
| **2** | **扶正第一个代码插件点**：菜单/配方解析器带上 manifest + 版本 + 失败隔离 | 版本不符时**拒装并出声**；解析器抛错只红它自己；现有外部解析器无需改逻辑即可接入 | 1 天 |
| **3** | **泛化到第二个点**：仪器原始格式适配器 | 一个新仪器的导出文件接入＝写一个适配器目录，不改宿主；产出仍过同一道闸 | 1–2 天 |

第 4 步（算法/GDS 插件化）**等真实需求**，不预先做。

---

## 五、反模式（明确不做）

- ⛔ **不做通用插件框架/插件市场/在线热插拔** —— 团队规模与需求都不支持；重启是秒级。
- ⛔ **插件不许直写 core 或资产库** —— 只许提议。
- ⛔ **不许插件自带口径** —— 任何插件产出都要过中心那道闸；否则"覆盖更多设备"会变成"更多口径分裂"。
- ⛔ **不一次铺开多个插件点** —— 每点都要契约/版本/测试/隔离，铺开必烂尾。

---

## 六、与其它规划的关系

- **与 A0-0（资产版本 + 改动留痕）同命**：插件没有版本就没法管；manifest 的 `name/version`
  直接复用同一套"资产版本 + 改动留痕"。
- **与 P2（权限分层）同批**：装插件＝管理员动作，走同一套角色与审批。
- **与公开层三条（案例留本地 · 规则进工具 · 身份只在内网）一致**：插件属"工具/规则"层；
  **插件里不许写内部案例数据或身份信息**（外发插件尤其）。
- **与"core 权威、不推断、留痕"三铁律一致**：插件的价值是**扩展输入与产出**，不是改写判据。

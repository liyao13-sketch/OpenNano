## 历史：当初的权衡（保留备查）



> 2026-09-13 定（工具线）。起因：owner问「我们的 UI 是否该区分全中文、全英文两种？全中文 UI 你有把握设计好吗？」

## 结论（一句话）

**该做，但做的是"语言切换 + 术语保真"，不是"两套界面"。** 中文是主语言（default），英文是第二语言；
**数据/术语（`run_id`/`stage_seq`/`core`/`PECVD`…）任何语言下都保持英文原样** —— 它们是契约里的键，翻成中文就再也对不上库了。

## 为什么"该做"

1. **我们已经在混排了**：界面文案是中文（"添加节点""适配视图"），而数据、工序名、参数键、状态值是英文
   （`RF Power`、`deposition`、`core:AR50-T1-ICP-0013`）。混排本身没错，但**没有规则**就会出现
   "同一个概念三处三种写法"（工具线踩过：`Deposition` / `薄膜沉积` / `deposition` 同屏出现）。
2. **对外/投稿要能看**：README 是英文的，界面全是中文。要给别人看（合作方、评审、GitHub 访客）时，
   英文界面是硬需求。
3. **一旦有规则，成本很低**：文案本来就没几处（我数过：界面字符串 ≈ 300 条，其中真正需要翻译的叙述性文案 ≈ 120 条）。

## 怎么做（分两步，别一口气重构）

**第一步（已完成 · 2026-09-13）· 中文优先的排版规则** —— 这是"全中文 UI 能不能设计好"的核心：

| 规则 | 为什么 |
|---|---|
| 中文标签**不放大字距**（用 `--track-cjk: .01em`，不用拉丁那套 `.05em`） | 中文加宽字距会散成"每个字独立"，很廉价 |
| 中文标签**不用 `text-transform: uppercase`** | 对中文无效，只会让同一排的英文突然变大写 |
| 正文行高 **1.5–1.6**（拉丁 1.3–1.4） | 中文方块字需要更多行距才透气 |
| 数字/单位/ID 一律**等宽 + tabular-nums** | 表格里数字要能对齐；`run_id` 要能逐字符比对 |
| 中英混排时**中文字号 = 拉丁字号**，靠字重而非字号做层级 | 拉丁的 x-height 比汉字视觉重心低，混排时"看起来"大小不一 |
| 标点用**全角**（，。：）但**括号内为英文时用半角半角空格包裹** | 中文排版规范；避免 `（core)` 这种半中半西 |

## 我有没有把握把"全中文 UI"设计好

**有，但要守住三条**（上面表格已经落地）：不放大字距、不用大写变换、行高给足。
另外两条中文界面特有的坑，我已经在别处踩过并写进规范：
- **窄容器里中文会逐字换行**（"知识库"竖成一列）⇒ 一律 `white-space: nowrap` + 不许被压缩（已修）；
- **中文比拉丁"占宽"**：同一个标签中文比英文短（"刻蚀" vs "Etch"）但也可能更长（"薄膜沉积" vs "Deposition"），
  所以**不许按英文字符数定列宽** —— 列宽由内容撑，窄了滚动（已在 `.tbl` 落地）。

## 不做什么

- ❌ 不做"两套界面"（两套 CSS/两套布局）—— 一定会漂移；
- ❌ 不翻译数据与术语（会破坏与 core/契约的对应关系，也违背零号铁律的精神：记录原样保存）；
- ❌ 不引入 i18n 三方库（我们只有两种语言、无复数/性别规则，一个对象 + 一个 hook 足够；少一个依赖少一份风险）。
